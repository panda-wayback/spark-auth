# Doc Node Graph — Pseudo Software

已裁定且需多模块协作实现时，在对应 docs 节点下展开伪软件设计。

## 流程

1. 理解需求；未理解前不写代码。
2. 将需求写成伪软件：功能、模块、输入、输出、模块契约、依赖、测试。
3. 用户裁定伪软件合理后，按 `ai-friendly-codebase` 生成/更新各模块 `spec.yaml` + `AI.md`，方可实现。
4. 每个模块实现时须明确输入、输出、遵守模块契约、通过独立测试。
5. 所有模块独立测试通过后，再进行组合测试。
6. 组合测试通过后，进行 Integration Test。
7. 禁止跳过步骤。

## 展开条件

- 能力节点已裁定。
- 实现涉及多个模块。
- 模块间有明确输入/输出/契约。

## 字段

| 字段 | 层级 | 内容 | 对应 `spec.yaml` 字段 |
|---|---|---|---|
| 功能 | 能力 | 本能力做成什么样；复用父节点 `目标` | 父级 `function` |
| 模块 | 能力 | 独立单元名称 | 父级 `modules` |
| 输入 | 每模块 | 模块接收的数据/事件/上下文 | `input` |
| 输出 | 每模块 | 模块返回的数据/事件/副作用 | `output` |
| 模块契约 | 每模块 | 行为保证、边界条件、失败模式、不变式 | `contract` / `errors` |
| 依赖 | 每模块 | 依赖的其他模块或外部能力 | `depends` |
| 独立测试 | 每模块 | 模块独立测试策略 | `tests` |
| 组合测试 / Integration Test | 能力 | 组合验证；端到端关键路径 | 父级 `tests` |

全部必填。模块拆分粒度：一个模块对应一个可独立理解、独立测试、有明确边界的责任单元。

## 写法

在父节点 `解决步骤` 中嵌入子节，或建独立子页：

```markdown
## 伪软件设计

### 功能

### 模块

| 模块 | 输入 | 输出 | 模块契约 | 依赖 | 独立测试 |
|---|---|---|---|---|---|
| A | … | … | … | … | … |
| B | … | … | … | … | … |

### 组合测试

### Integration Test
```

## 实现约束

- 实现须以伪软件为准；禁止偏离模块契约。
- 未通过独立测试的模块禁止组合。
- 组合前确认模块间接口对齐、依赖已就绪。
- 组合测试未通过禁止 Integration Test。
- Integration Test 覆盖本能力端到端关键路径；不通过时回退到组合或模块层定位问题。

## 与能力节点的关系

- 伪软件不替代能力节点；能力节点保留 `目标` / `要实现的` / `解决步骤`。
- 伪软件作为 `解决步骤` 中某一步的详细展开，或作为子页链接。
- 伪软件裁定后，若父节点 `解决步骤` 未体现，须同轮更新。
- 各模块 `spec.yaml` 生成后，docs 中模块表替换为指向各模块 `spec.yaml` 的链接；契约只以 `spec.yaml` 为准。
- 实现中契约需变更 → 按 `workflow.mdc` 裁定后改 `spec.yaml`；docs 只在能力级目标/步骤变化时改。

## 禁止

- 单一模块或简单改动强制展开伪软件。
- 把伪软件写成代码说明书。
- 在伪软件中写死本仓业务模块表或产品名词。
